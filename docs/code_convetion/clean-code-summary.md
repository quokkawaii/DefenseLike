# 클린 코드 요약 (로버트 C. 마틴, *Clean Code*)

- 상태: `제안` (프로젝트 규칙으로 쓰려면 사용자 승인 필요)
- 근거: 로버트 C. 마틴 저, *Clean Code: A Handbook of Agile Software Craftsmanship* (2008)의 주요 주장을 에이전트가 자기 말로 요약한 문서이다. 책의 문장을 옮긴 것이 아니며, 원문 확인은 책을 직접 참고한다.
- 용도: 코드 리뷰와 QA에서 "재활용성·확장성이 있는 코드인가"를 판단하는 공통 언어로 쓴다. 이 프로젝트 전용 기준은 `code-standard.md`에 따로 둔다.

## 1. 핵심 전제

- 코드는 쓰는 시간보다 읽는 시간이 훨씬 길다. 읽기 쉬운 코드가 곧 수정하기 쉬운 코드다.
- 코드를 만질 때는 처음 봤을 때보다 조금 더 깨끗하게 남긴다(보이스카우트 규칙).
- "나중에 정리하겠다"는 대개 실행되지 않는다. 엉망인 코드는 속도를 늦춘다.

## 2. 이름 짓기

- 이름은 의도를 드러내야 한다. 주석 없이 "무엇을, 왜"가 읽혀야 한다.
- 그럴듯한 오해를 부르는 이름(`list`가 실제로는 Set)을 피한다.
- 의미 있는 차이를 만든다. `data1`, `data2`, `info`, `manager` 같은 군더더기 이름을 피한다.
- 발음 가능하고 검색 가능한 이름을 쓴다. 매직 넘버는 이름 붙은 상수로 바꾼다.
- 클래스는 명사, 메서드는 동사. 한 개념에는 한 단어만 쓴다(`get`/`fetch`/`retrieve` 혼용 금지).

## 3. 함수

- 작아야 한다. 더 작아야 한다.
- 한 가지 일만 한다. 함수 안의 모든 문장이 같은 추상화 수준에 있어야 한다.
- 위에서 아래로 읽히게 쓴다(상위 개념 → 세부).
- 인수는 적을수록 좋다(0~2개). 플래그 인수(boolean)는 "두 가지 일을 한다"는 신호다.
- 부수 효과(숨은 상태 변경)를 만들지 않는다. 출력 인수를 피한다.
- 명령과 조회를 분리한다. 값을 바꾸는 함수가 동시에 값을 돌려주지 않게 한다.
- 오류 코드 반환보다 예외가 낫다. try/catch 본문은 별도 함수로 뺀다.
- 중복(DRY)은 소프트웨어 악의 근원이다.

## 4. 주석

- 좋은 주석은 코드로 표현하지 못한 **의도**와 **이유**를 적는다. 나쁜 코드에 주석을 덧칠하지 말고 코드를 고친다.
- 코드가 말하는 내용을 되풀이하는 주석, 오래돼 거짓이 된 주석, 주석 처리한 코드, 변경 이력 주석은 지운다.
- 허용되는 주석: 법적 고지, 의도 설명, 결과 경고, TODO, 공개 API 문서.

## 5. 형식

- 신문 기사처럼: 파일 위쪽에 고수준 개념, 아래쪽에 세부.
- 관련 있는 코드는 세로로 가깝게, 무관한 코드는 빈 줄로 분리한다.
- 변수는 사용 위치 가까이에서 선언한다. 한 줄 길이를 짧게 유지한다.
- 팀은 하나의 형식 규칙을 공유하고 자동화(포매터·린터)에 맡긴다.

## 6. 객체와 자료구조

- 객체는 동작을 노출하고 데이터를 숨긴다. 자료구조는 데이터를 노출하고 동작이 없다. 둘을 섞은 잡종 구조를 피한다.
- 디미터 법칙: 객체는 자신이 모르는 객체의 내부를 파고들지 않는다(`a.getB().getC().do()` 지양).
- 데이터 전송 객체(DTO)는 순수한 데이터 구조로 둔다.

## 7. 오류 처리

- 오류 처리는 한 가지 일이다. 정상 흐름을 가리지 않게 분리한다.
- `null`을 반환하거나 전달하지 않는다. 호출자가 방어 코드를 도배하게 된다.
- 예외에는 상황을 알 수 있는 정보를 담는다.

## 8. 경계

- 외부 라이브러리·프레임워크는 직접 퍼뜨리지 말고 경계에 감싼다. 교체·업데이트 비용이 줄어든다.
- 외부 코드를 쓸 때 학습용 테스트로 동작을 확인한다.

## 9. 단위 테스트

- TDD 3법칙: 실패하는 테스트 없이 코드를 쓰지 않는다 / 실패하기에 충분한 만큼만 테스트를 쓴다 / 통과하기에 충분한 만큼만 코드를 쓴다.
- 테스트도 클린해야 한다. 가독성이 가장 중요하다.
- 테스트당 개념 하나. F.I.R.S.T: 빠르고(Fast), 독립적이고(Independent), 반복 가능하고(Repeatable), 자가 검증되고(Self-validating), 적시에 작성한다(Timely).

## 10. 클래스

- 작아야 한다. 크기는 줄 수가 아니라 **책임**의 수로 잰다.
- 단일 책임 원칙(SRP): 변경할 이유가 하나뿐이다.
- 응집도가 높아야 한다. 메서드들이 인스턴스 변수를 함께 쓴다.
- 변경에 열려 있고 수정에 닫혀 있게(OCP) 설계한다. 구체 구현이 아니라 추상에 의존한다(DIP).

## 11. 시스템

- 생성(조립)과 사용을 분리한다. 의존성 주입으로 결합을 낮춘다.
- 처음부터 완벽한 구조를 만들려 하지 말고, 오늘 필요한 만큼 만들고 리팩터링으로 키운다.
- 관심사를 분리한다.

## 12. 창발적 설계 (켄트 벡의 4규칙)

우선순위 순서로:

1. 모든 테스트를 통과한다.
2. 중복이 없다.
3. 프로그래머의 의도를 표현한다.
4. 클래스와 메서드 수를 최소로 한다.

## 13. 냄새와 휴리스틱 (리뷰 체크용 발췌)

- 중복, 죽은 코드, 일관성 없는 표기
- 너무 많은 인수, 플래그 인수, 부수 효과
- 기능 부러움(Feature Envy): 다른 클래스의 데이터를 계속 만지는 메서드
- 매직 넘버, 불명확한 이름, 불필요한 주석
- 서로 다른 추상화 수준의 혼합, 과도한 정보 노출
- 테스트가 부족하거나 경계 조건을 빼먹음
