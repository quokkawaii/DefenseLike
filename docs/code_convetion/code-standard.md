# DefenseLike 좋은 코드 기준 (쉬운 버전)

- 상태: `제안` (에이전트 의견, 사용자 승인 전)
- 근거: `clean-code-summary.md`, `SYS-132`(Phaser와 규칙 계산 분리), `SYS-074`(Vitest)
- 목적: "이 코드가 재활용·확장하기 좋은가"를 판단할 때 쓰는 짧은 체크리스트

## 한 줄 요약

> 계산은 Phaser 밖에, 값은 JSON에, 화면은 Scene에. 한 함수는 한 가지 일만.

## 체크리스트 (8개)

| # | 질문 | 나쁜 예 | 좋은 예 |
|---|---|---|---|
| 1 | 계산과 화면이 분리돼 있나? | Scene 안에서 피해량 계산 | `src/func/`에서 계산, Scene은 결과만 그림 |
| 2 | 값이 코드에 박혀 있지 않나? | 코드에 `if (hp < 30)` | JSON에 값을 두고 읽어서 사용 |
| 3 | 함수가 한 가지 일만 하나? | `create()` 하나가 경로·칸·포탈을 전부 그림 | `drawPath()`, `drawCells()`, `drawPortals()`로 분리 |
| 4 | 이름만 읽어도 뜻이 보이나? | `d`, `tmp`, `data2` | `spawnPoint`, `cellCenter` (요구사항 문서의 용어) |
| 5 | 같은 코드가 두 군데 있나? | `FIELDS` 배열을 두 파일에 각각 정의 | 한 곳에서 정의하고 가져다 씀 |
| 6 | 새 종류를 추가할 때 기존 코드를 고쳐야 하나? | 몬스터마다 `if`/`switch` 추가 | 데이터만 추가하면 됨 |
| 7 | Phaser 없이 테스트할 수 있나? | 테스트하려면 게임 창이 필요 | `func` 함수는 `npm test`로 바로 검증 |
| 8 | 요구사항에 근거가 있나? | 근거 없는 함수·숫자 | 주석에 요구사항 ID가 있음 |

## 폴더 규칙 (이미 `SYS-134`에 있는 내용)

- `src/content/` : JSON 데이터
- `src/types/` : 타입
- `src/func/` : 계산 함수 (Phaser 사용 금지)
- `src/game/` : Phaser 화면 (Scene)

## 주의

- 미리 만들어 두는 "범용" 코드는 만들지 않는다. 지금 요구사항에 필요한 것만 만든다.
- 기준끼리 충돌하거나 판단이 어렵다면 사용자에게 묻는다.

## 리뷰할 때

각 질문에 `예 / 아니오`로 답하고, `아니오`는 파일과 줄 번호를 함께 보고한다. 고치는 것은 사용자가 요청한 뒤에 한다.
