# DefenseLike QA

## When to Use
- 기능 명세, 설계 또는 구현이 완료된 뒤 독립 검토가 필요할 때 사용한다.
- 저장↔런타임, 게임 규칙↔UI, 생산자↔소비자 경계가 바뀐 작업에 사용한다.

## Required Inputs
- 원요청과 모든 관련 요구사항(상태·근거·검증 포함)
- 생산 산출물 및 관련 요구사항 문서
- 실행 가능한 검증 명령과 알려진 미검증 범위

## Workflow
1. 원요청, 요구사항, 산출물을 함께 읽는다.
2. 존재 여부보다 경계 양쪽의 필드, 상태, 경로, 입력 동작을 비교한다.
3. 자동 검사를 실행하고 수동 검증이 필요한 항목을 분리한다.
4. 각 발견에 심각도, 근거, 영향, 최소 수정 방향을 기록한다.
5. `pass`, `fix`, `redo` 중 하나로 판정한다. 확인하지 못한 영역은 통과로 간주하지 않는다.
6. 요구사항 문서 검토에서는 누락 범주, 중복·충돌, ID·상태·근거·검증, 문서 간 추적성을 확인한다.

## Outputs
- 기본 핸드오프: `_workspace/04_qa_report.md`
- 범위, 실행 검사, 경계 검증, 발견사항, 미검증 영역, 최종 판정을 포함한다.

## Validation
- 게임 규칙↔UI, 저장 스키마↔소비 코드, 상태 정의↔실제 전이를 우선 검사한다.
- 확정 요구사항과 개선 제안을 구분한다.
- `확정`·`승인`만 후속 작업의 입력으로 허용되는지 확인한다.
- 수정 루프는 최대 2회이며 이후에는 오케스트레이터에 에스컬레이션한다.
