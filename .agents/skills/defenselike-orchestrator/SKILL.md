# DefenseLike Orchestrator

## When to Use
- 여러 요구사항 문서나 코드 영역을 함께 다루는 기능 개발에 사용한다.
- 기획 확정, 시스템/UX 설계, 구현, QA 사이의 핸드오프가 필요한 요청에 사용한다.
- 한 파일의 단순 수정처럼 한 에이전트가 충분한 작업에는 팀을 만들지 않는다.

## Required Inputs
- 최신 `AGENTS.md`와 사용자 요청
- 관련 요구사항 문서 및 현재 코드/테스트 상태
- 변경 가능한 경로와 검증 기준

## Workflow
1. 요청을 `_workspace/00_input/request-summary.md` 형식으로 정리하되, 세션 간 인계가 필요할 때만 실제 파일을 만든다.
2. 항목을 `확정`, `제안`, `미정`, `승인`으로 분류하고 충돌을 먼저 찾는다.
3. `docs/harness/defenselike/team-spec.md`의 라우팅 표에서 필요한 역할만 선택한다.
4. 독립적인 읽기/분석은 병렬화할 수 있다. 공유 체크아웃 쓰기는 경로가 겹치지 않을 때만 병렬화하고, 아니면 직렬화한다.
5. 요구사항 문서는 기획 문서를 겸하며, QA가 원요청·공식 근거·문서 간 경계를 교차 검증한다.
6. QA 결과가 `fix`이면 최대 2회 수정한다. `redo` 또는 핵심 충돌이면 사용자에게 보고한다.
7. 사용자가 항목별로 리뷰한다. 통과 항목은 `승인`, 수정이 필요한 항목은 `제안` 또는 `미정`으로 유지한다.
8. 시각 디자인과 구현은 `확정`·`승인` 요구사항만 소비하며 각 산출물에 근거 ID를 남긴다.
9. 오케스트레이터가 최종 통합, 검증 결과, 남은 미정 사항을 종합한다.

## Outputs
- 필요 시 `_workspace/01_requirements-draft.md`
- 필요 시 `_workspace/02_architecture_technical-design.md`
- 필요 시 `_workspace/02_ux_interaction-spec.md`
- 필요 시 `_workspace/03_implementation_result.md`
- 필요 시 `_workspace/04_qa_report.md`
- 사용자 요청에 따른 코드 또는 문서 최종 산출물

## Validation
- 모든 역할이 같은 요구사항 스냅샷을 사용했는지 확인한다.
- 각 변경 파일의 소유자가 하나인지 확인한다.
- QA는 생산자와 소비자 양쪽 경계를 검사하고 `pass`, `fix`, `redo` 중 하나를 반환해야 한다.
- 사용자 승인 전에는 `제안`·`미정`을 디자인·구현 단계로 넘기지 않는다.
- 누락된 역할, 실패한 검사, 해소되지 않은 충돌을 성공으로 꾸미지 않는다.

## Failure Handling
- 역할 생성/도구/권한 실패: 오케스트레이터가 가능한 범위를 직렬 수행하고 누락 범위를 명시한다.
- 쓰기 충돌: 병렬 작업을 중단하고 한 소유자에게 직렬 배정한다.
- 부분 실패: 기존 산출물을 보존하고 최종 상태를 `partial` 또는 `blocked`로 표시한다.
- 통신 실패: 결정과 차단 사유를 결정적 `_workspace/` 파일로 남긴다.
